# 05 · 核心业务逻辑

> **30 秒版**：这个 App 只有一条核心规则 —— **一天 1440 分钟，每一分钟都要有归属**。
> 其余所有逻辑（切事项、改时间、模板、统计）都是这条规则的推论。
> 这篇讲清楚它们到底怎么算。

---

## 30 秒版：一句话概括全部

```
一天 = 1440 个格子
每一段记录 = 占掉其中连续的一段 [a, b)
所有段首尾相接、加起来 1440 → 这一天才算「对」
```

「未记录」不是「没有格子」，而是**一格一格记下来的「没在记」**。
所以它也是一段，也有 id，也能被点击补记。

---

## 上手版：六条规则

### 规则 1 · 时间用「分钟」存，不用时间戳

```kotlin
startMin = 480   // 08:00
endMin   = 570   // 09:30
```

为什么不存 `1700000000`（时间戳）？
因为**分钟的加减是整数运算**：8:00 到 9:30 就是 `570 - 480 = 90` 分钟，不需要处理时区、夏令时、闰秒。

代价是不存秒。这个 App 的精度就是分钟 —— **刻意如此**，不是偷懒。

### 规则 2 · 密铺（Dense）：每天都得接上

任何一天的所有段，必须满足：

1. 第一段从 **0** 开始
2. 最后一段到 **1440** 结束
3. 相邻两段 `前一段.b == 后一段.a`

`domain/Density.kt` 就是干这个检查的。**每一天导入、每次大规模写入之后都会跑一遍**，
不通过就整包不写。

### 规则 3 · 「有未来」和「有空白」是两件事

- **历史日**：必须铺满 `[0, 1440]`
- **今天**：只铺到 **此刻**（`cut`），之后的时间不铺 —— 因为还没发生

所以「今天」的 `1440 - cut` 分钟**既不是已记录也不是未记录**，它不存在。
统计时它也不进分母。这条如果搞错，你早上打开统计会看到「我 95% 时间都在浪费」。

### 规则 4 · 切事项：一次操作，两个动作

点「结束」→ 选一个事项，实际发生了：

```
旧那一段 .b  ←  此刻          （把上一件收在现在）
新那一段 [此刻, null) 开始     （endMin = null 表示「还在进行中」）
```

`endMin = null` 是「进行中」的标记，全库最多只有**一条**。

### 规则 5 · 改时间：撞车不等于产生空隙

把 A 段的结束时间往后推，撞到了 B 段怎么办？

**邻居让位** —— B 段的起点跟着往后挪；如果 B 完全被盖住，就把 B 删掉。
**一律不弹窗**，改完用底部提示条逐条说明「影响了哪几段」。

这里的关键认知：**「撞车」和「产生空隙」是两回事**。
撞车是邻居被压短（数据仍然密铺）；空隙是你把一段缩回去，中间露出了没记的时间（变成 GAP）。

### 规则 6 · 删除 = 原地擦成空白

删一段记录，**不是从数据库 DELETE 掉**，而是把它原地 UPDATE 成一条 `GAP`。
删完立刻变「未记录」，并给 4 秒撤销机会。

为什么不 DELETE？因为删掉就留了一个**洞**，而洞会让「一天恒 1440」这个不变式失效。
原地改标记，坑还在，只是变成了「这里没记」。

⚠️ 唯一例外：**零长度的段**、以及**被合并吸收的相邻空白**，允许真 DELETE。

## 深挖版：几处最容易写错的地方

### ① 模板运行模型（最容易做错的一块）

模板 = 给周一到周日各配一张日程表。启用后它把**已经过去**的时间里的空白填上。

四条必须记住的规则：

**a. 懒结算，不依赖后台**

```
你 8:00 上班、开模板、中午 12:00 才拿起手机
→ App 一打开，一次性把 8:00~12:00 按模板铺好
```
结果是「晚几小时补上」和「准点实时填」**完全一样**。所以根本不需要后台常驻。

**b. 只填空白，绝不覆盖手记的**

模板的判断函数（`fillableByTemplate`）有三条：

| 这段是什么 | 能不能被模板填 |
|---|---|
| 空白（GAP）且没被手动清过 | ✅ 可以 |
| 模板自己铺的、还「进行中」那一条 | ✅ 可以重切 |
| 模板自己铺的、已经结束了 | ❌ 不可以 |
| 你手记的 | ❌ 永远不可以 |

⚠️ **第二行漏掉的后果**：12:00 铺的「午休 `[12:00, 现在)`」会一路滚到 20:00 都切不开，
不报错、不崩，就是「模板好像卡住了」。

**c. 配置 ≠ 启动**

配好日程表什么都不发生。必须显式点「启用」。
**退出只认一个动作：点「结束」并亲手选别的事项。**
改记录、删记录、改模板都**不算**退出 —— 那三件事和「我现在在干什么」无关。

**d. 运行中改模板 → 正在执行的那一段按【旧】模板跑完**

不然你改一下模板，正在进行的这一段会瞬间变样，看着像数据错乱。
实现上靠「运行态段快照 + revision 递增」。

**刷新链的顺序是死的：**

```kotlin
syncTemplateDay()   // ① 跨天了没
carryOver()         // ② 昨天的尾巴接到今天
ensureDense(day)    // ③ 补齐到此刻
applyTemplate(day)  // ④ 模板填空白
```

- ③④ 反了 → 互相打架
- ② 挪到 ③ 后面 → **再也不接续，且不报错**（③ 的自愈会把「非今天的进行中记录」就地封口）

### ② 跨天：那条 1440 与 0 的缝

23:58 上床、次日 7:30 起。做法：

```
前一天：[23:58, 1440)  睡觉   chainId = X
后一天：[0, 7:30)      睡觉   chainId = X     ← 同一个 X 表示是同一件事
```

⚠️ **终点必须是 1440，不是 1439**。
写成 1439 每天永久丢 1 分钟，一年丢 6 小时，而且**永远不会报错**。

次日的第一段自动接续同一事项，**零提示、零弹窗**。
也**不做**「你是不是忘了切」的提醒 —— 睡觉本来就 8-9 小时，天天亮警示就是噪音。

### ③ 统计口径：分母到底是什么

```
占比 = 某事项分钟数 ÷ 到此刻的分钟数
```

- 历史日：分母 = 1440
- 今天：分母 = 从 0 点到此刻（`cut`）
- **「未记录」也算在分母里** —— 所以「已记录率」是诚实的

⚠️ 改事项的归属分类时，**历史统计跟着重算**（按事项**当前**的分类）。
记录里存的 `categoryIdSnap` 只是留档，统计不用它。

### ④ 撤销是怎么做的

每次「可能后悔的操作」之前，先写一份 `backup_snapshots` 快照，然后才动数据。
撤销 = 把快照里的记录写回去。

⚠️ 快照是**一次性**的：撤销一次就删掉。「多级撤销」在这个场景是负价值 ——
你不知道自己撤到的是哪一步。

### ⑤ 删除前的守卫必须在数据层

「分类下还有事项就不许删分类」「标签桶里还有标签就不许删桶」——
这两条**不能只在界面上把按钮置灰**，因为别的入口（比如以后加的批量操作、脚本）照样能调进来。

所以 `canDelCat` / `canDelTag1` 的判断写在 Repository 里，函数内部也拒绝。

⚠️ 但这两件事的**连带影响完全不同**，别照抄实现：

| 关系 | 语义 | 删了会怎样 |
|---|---|---|
| 分类 → 事项 | **归属**（决定颜色 + 统计口径） | 换归属要重算统计 |
| 一级标签 → 二级标签 | **纯容器** | 换桶、删桶**不动任何记录、不改统计** |

## 一张图总结

```
        你的一次点击
             │
             ▼
    ┌─────────────────┐
    │  TimelineRepository  │   ← 所有业务规则的落点
    │  · pick()       │       切事项
    │  · editTime()   │       改时间（含撞车让位）
    │  · delete()     │       原地变 GAP
    │  · ensureDense()│       补齐到此刻
    │  · applyTemplate│       模板填空
    └────────┬────────┘
             │ 每一步都保持「一天 1440 密铺」
             ▼
    ┌─────────────────┐
    │   Room (SQLite)  │
    └────────┬────────┘
             │
             ▼
    ┌─────────────────┐
    │  domain/ 纯函数  │  ← 界面用的所有计算都在这里（可测）
    └─────────────────┘
```

想验证「我理解了」，最好的办法是去看 `TimelineRepositoryTest` ——
那里每个测试名就是一句业务规则的白话。
