## 深挖版

### ① 跨天终点写成 1439 —— 每天丢一分钟，永远不报错

**症状**：没有任何症状。统计里的日总计是 1439 而不是 1440。

**根因**：`[23:58, 1439)]` 表示「到 23:59」，而按分钟计的区间终点应该是 **1440**（= 24:00）。
差这一分钟，一年丢 6 小时。

**修法**：跨天段的 `endMin` 恒为 `MINUTES_PER_DAY`（1440），次日的 `startMin` 恒为 0。

**教训**：**「一天 1440 分钟」这句话必须落成一个常量、一条断言，而不是一句口号。**
现在 `DensityTest` 里有一条专门断言「每天加起来恰好 1440」——
这条测试存在的意义不是发现 bug，是**防止某天有人觉得 1439 更自然**。

### ② `noTemplate` 锁会自己「长大」 —— 本项目最阴的一个

**症状**：「模板明明运行中，但整块显示未记录」。而模板的运行态、日期、星期指派**全部正常**，
日志一个错都没有。

**现场**（某天真机数据）：
```
12:23-12:48  吃饭     MANUAL
12:48-14:29  (空白)   GAP   noTemplate = 1   ← 保护了 102 分钟
```

**根因**：`noTemplate` 的本意是「这**几分钟**我不想要模板填」（删记录时留下的）。
但它挂在一条**空白记录**上，而补密逻辑每次刷新都会把**尾部空白延长到此刻** ——
标记就跟着「此刻」一起往前爬：

```
12:48 删掉 3 分钟 → [12:48, 12:51) 带标记     本意：就这 3 分钟
12:51 刷新        → [12:48, 12:52) 带标记     延长时把标记一起带走了
14:30 刷新        → [12:48, 14:30) 带标记     保护了 102 分钟
```

**修法**（三条，缺一不可）：
1. `ensureDense` **不许延长**带标记的尾部空白 —— 冻在原处，从它的终点另起一条干净的
2. 启用模板时清掉**紧贴此刻那一条**的标记（「从现在起照模板来」应该覆盖「那几分钟别填」）
3. 标记本身**照常有效**（不然「删掉模板记录」会重新变成删不掉）

**⚠️ 试过又撤回的方向**：「带标记和不带标记的相邻空白不合并」。
看似能把锁圈死在原地，实际打红了三条存量测试 ——
**删记录产生的空白必然带标记，紧邻的空白不带**，于是删一下就碎成一串「未记录」。

**教训**：**当一个标记挂在「会自动变化的容器」上时，它一定会跟着容器一起漂。**
正确的做法是让容器停止变化（不延长），而不是去修补所有受它影响的下游逻辑。
根子只有一个，别在症状上打补丁。

这条现在有 6 条专门的测试（`TemplateNoTemplateLockTest`）盯着。

### ③ 为了让细段好点，把段画高了 —— 图形不能说谎

**症状**：22 分钟和 23 分钟两段（真实高度各约 11dp）**重叠了 11dp**，名字糊成一团。

**根因**：为了让 10 分钟的段也能点中，把段的显示高度抬到 22dp。
问题是一天有多少段就画多少个 22dp，总高度远超屏幕 → 重叠。

**根本错误**：**让图形比真实时间长。**
这和「缝隙必须可见」是同一个根 —— 时间轴一旦撒谎，这个 App 的地基就塌了。

**修法**：
- 段**按真实高度画**，只兜一个 `2dp` 的「至少有像素」下限
- 点击判定改成**按分钟反查坐标**（`domain/MinuteHit.kt`），不靠加粗换命中率
- 新增 `SegGeometryTest`（13 条**纯坐标**断言）

**⚠️ 一个连带的差 1dp 问题**：「满 1 小时」原本按显示高度判（`>= 30dp`），
但 60 分钟算出来是 29dp（扣掉 1dp 段间缝）→ 「整点一小时」的事项反而**显示不出时间**。
改成 `SegGeometry.showsTimeLine(durationMin)` —— **按时长判，不拿像素表达时间概念**。

**教训**：**「画得对」和「点得中」是两件事。**
需要提高命中率时，去改**判定逻辑**，不要改**视觉呈现**。

### ④ 同一个状态在三个地方各刷一遍 —— 唯一入口（栽过 8 次）

**症状**：在 A 处改的设定，回到 B 处又变回去了。

**发过的事故**（同一类问题的八个实例）：

| 事故 | 表现 |
|---|---|
| 周条不可点 | 一周的条画出来了，但点了没反应 |
| 周条不跟翻页 | 翻到下一周，条还显示上一周 |
| 网格顺序不跟分类 | 改了分类顺序，选择面板没变 |
| 底部「结束」条不跟页面 | 切了 tab，底部还显示昨天的事项 |
| 模板页不跟配置 | 改了模板，运行态显示没变 |
| 统计图热区不跟柱子 | 见第 ⑥ 条 |
| 小部件各抄一份刷新链 | 小部件和 App 显示的「当前事项」不一致 |
| 选事项面板三处各写一份 | 小部件里切了聚合视图，打开 App 又变回分组 |

**修法**：把状态收拢到一个入口，所有显示方都从它取。

现在的唯一入口清单：
```
viewDay(d)              时间线看哪一天
refreshAll()            界面全量刷新
catBlocks()             分类分块顺序
TimelineRepository.maintain(day)   真机侧刷新链（主界面/小部件/悬浮窗共用）
PickerHost              选事项面板的共享状态
ChartGeom               统计图的坐标换算
```

**教训**：**凡声称「跟 X 走」的，必须有唯一一个地方负责同步，并且测试里有一条不变量断言。**
⚠️ 而且**真机侧比原型侧更容易犯** —— 每加一个「不用打开 App 的入口」，
就多一个需要刷数据的地方，你不主动收口，就一定有人各抄一份。

### ⑤ 图画对了，但点不到 —— 热区不跟柱子

**症状**：统计图上的柱子看起来在正确位置，点它没反应；点旁边一点反而有反应。

**根因**：柱子用一套坐标算、点击热区用另一套坐标算。两套算法在**边界**上差了几像素。

**修法**：热区也走同一个 `ChartGeom`，不给它第二套算法。

**教训**：
- 「只断数据不够，还要断几何」
- 「几何对了还不够，还要断**交互热区跟几何对齐**」
- 三者都**不报错、不崩、截图看不出来**

所以现在凡是几何渲染（时间线、图表、月历、模板色条），都必须有一条
**只看坐标、不看数据**的断言。

### ⑥ `GlanceAppWidget.updateAll()` 约七成是「假刷新」

**症状**：桌面小部件的数据经常慢一拍，重启桌面就好。

**根因**：`updateAll()` 会**立刻返回**（2~15ms），但 `provideGlance` 根本没进去执行，
只是把上一帧又推了一遍。

**修法**：读库 → `updateAppWidgetState` 改一个 `rev` 值 → 再 `updateAll`。
改了 state 才会真正触发重绘。刷新挂到 `TimelineViewModel.reload()` 末尾。

**教训**：**「调用成功」不等于「事情发生了」。**
对这类「异步副作用」的 API，光看返回值不够，得有一个能观察到的结果变化（这里是 `rev`）。

### ⑦ 断言直接调函数，绕过了按钮 —— 修好了但没接上线

**症状**：功能「实现了」，测试全绿，但界面上那个按钮点了没反应。

**根因**：断言写的是 `eval("calNav(1)")` —— 直接调用函数，**绕过了按钮的 onclick**。
而 onclick 那行还是占位符 `{}`。

**教训（本项目最重要的一条测试方法论）**：
> **按钮该干的事，断言必须去点那个按钮**，并顺带断言它不是占位。

因为**接线**才是容易错的地方，函数本身往往是好的。
直接调函数等于把最容易错的那一环跳过然后宣称验过了。

---

### ⑧ 「有没有这个功能」看数据变没变，不看按钮上写了什么

**症状**：连着七次「以为做了，其实没做」。

**根因**：按钮的文案、位置、图标全对，就是没接 onClick。
光看界面（甚至看代码里按钮写得好不好）都判断不出来。

**修法**：判断标准改成 —— **点了之后数据变没变**。

⚠️ 而且**长得像的入口一半真一半假，必须逐个验**，不能验一个就推广到一片。

### ⑨ 靠截图目测 —— 三次看错

**三次真实误判**：
- 把**浅灰的柱子**看成「中间有白缝」
- 把 **0 个**琥珀色像素看成「有红点」
- 把「两段重叠」看成「正常相连」

**修法**：从 DOM / 像素里**把数值抠出来核对**，不看图。

例如验证日历上的黄点：不是截图看，而是数「10 月里哪些天有 GAP」，
再和数据库里的日期集合做差集 —— 要求**零误报零漏报**。

**教训**：截图能证明「渲染出来了」，不能证明「渲染对了」。

### ⑩ Gradle 在后台跑的时候改源码 —— 白等两轮

**症状**：等了 7 分钟，编译失败/测试失败，但代码看起来是对的。

**根因**：编译读到的是**改到一半的文件**。Kotlin 编译是批量读源码的，
你 `Edit` 到一半它读到的就是半成品。

**修法**：Gradle 跑着的时候只做**非源码**的事（写文档、看数据、查日志）。

**⚠️ 另一个相关的坑**：`Edit` 替换 `if/else` 分支时**很容易吞掉闭合括号**。
症状是编译报 `Expecting '}'` 指向一个完全无关的行号。
改完 `if/else` 立刻读回那一段确认结构。

### ⑪ 把截图的显示尺寸当成真机像素

**症状**：脚本算好的坐标 `(990, 650)`，点下去点到了屏幕另一处，把面板关掉了。

**根因**：截图是 1080×2400，但看图工具把它缩放显示成 486×1080。
按显示尺寸点的位置，在真机上差了 2.2 倍。

**修法**：**一律用 `uiautomator dump` 拿到真实 bounds 再点**，不要从截图量比例。

**教训**：跟第 ⑨ 条同源 —— **能用数值就别用眼睛**。

---

### ⑫ 代理没开，所有网络请求都「挂了」

**症状**：`curl` 返回 `HTTP 000` / `Couldn't connect`，看起来像接口挂了或者被墙了。

**根因**：环境变量里配着 `https_proxy=127.0.0.1:7897`（机场客户端），但客户端**没启动**。
于是所有请求都往一个没人监听的端口上发。

**修法**：`curl --noproxy '*'`，或者先确认代理真的在跑。

**教训**：**排错时要先排除「环境自己有问题」这一层。**
这个坑在这个项目里出现了两次（curl 一次、Node CLI 一次），
症状都长得像「对方的服务坏了」，很容易误判。

## 如果你只记一条

**每个「看起来好了」的结论，都要问一句「我是怎么知道的」。**

上面 12 条里，有 8 条之所以拖了很久，不是难修，而是**一开始的判断是错的**：
- 以为按钮接好了 → 其实只验了函数
- 以为图画对了 → 其实只看了截图
- 以为接口挂了 → 其实是本地代理
- 以为代码对 → 其实编译读了半成品

判断方法上的错误，比代码里的错误贵得多。
