# 04 · 代码结构导览

> **30 秒版**：14 个包，一句话说清各自管什么，再给一条最短阅读路径。
> 不用从头读到尾 —— 这个项目按「依赖方向」分层，顺着箭头读就行。

---

## 30 秒版：依赖方向

```
        ui/  (Compose 界面)
         │  只能往下调
         ▼
     data/repo/  (业务规则真正落在这里)
         │
         ├──► data/dao/ ──► data/entity/  (数据库)
         │
         └──► domain/  (纯 Kotlin，不 import 任何 android.*)
                            ▲
      cloud/  widget/  ────┘ 也走同一套 repo
```

**关键规矩：`domain/` 不许 import `android.*`。**
这不是洁癖 —— 因为只有这样，那 16 个文件里的逻辑才能用普通 JVM 测试
（不需要模拟器、不需要真机、一秒钟出结果）。整棵树的测试能跑这么快，全靠这一条。

## 上手版：14 个包逐个说

### 根目录（3 个文件）

| 文件 | 干什么 |
|---|---|
| `TimeLogApp.kt` | `Application`，创建 `AppContainer` |
| `AppContainer.kt` | **手写依赖注入**：数据库、各种 Repository、各种 Prefs 都在这建 |
| `MainActivity.kt` | 唯一一个 Activity，管底部导航和路由 |

> 为什么不用 Hilt/Koin？全项目只有二十来个对象，一个 `AppContainer` 加构造参数就够了。
> 引 DI 框架会多一层「东西从哪来」的间接，对读代码的人是负担。

### `data/` —— 数据层

| 包 | 内容 | 说明 |
|---|---|---|
| `data/entity/` | 11 个 `@Entity` 类 | 表结构。`RecordEntity` 是核心，其余是字典和模板 |
| `data/dao/` | 7 个 `@Dao` 接口 | 只写 SQL，不写业务 |
| `data/repo/` | 5 个 Repository | **业务规则几乎全在这里** |
| `data/import/` | 旧数据导入 | 解析 JSON → 校验 → 写库 |

**5 个 Repository 各管什么：**

| 文件 | 行数 | 管什么 |
|---|---|---|
| `TimelineRepository.kt` | ~2600 | ★ **心脏**。记录的一切：切事项、改时间、删、补密、模板应用、撤销 |
| `CatalogRepository.kt` | ~500 | 分类/事项/标签的增删改，以及删除前的守卫 |
| `StatsRepository.kt` | ~300 | 统计查询（把库里的段喂给 `StatsCalc`） |
| `TemplateRepository.kt` | ~400 | 模板的增删改、启用/停止、运行态 |
| `ItemColors.kt` | ~150 | 事项配色的**唯一解析入口** |

> 想读懂这个项目，**`TimelineRepository` 是绕不过去的一课**。它长，但每一段都有注释说
> 「为什么是这样，试过别的什么做法」。建议配合 `TimelineRepositoryTest` 一起看。

### `domain/` —— 纯逻辑（16 个文件）

这一层是整个项目**最值得抄走**的部分，因为它不依赖 Android、全是纯函数。

| 文件 | 干什么 | 被谁用 |
|---|---|---|
| `Density.kt` | 判断一天有没有接上、有没有重叠 | 到处都在用 |
| `Overlap.kt` | 区间运算：撞车时谁让位、相邻空白能不能合并 | 改时间、删记录 |
| `SegGeometry.kt` | 时间线上每段该多高、什么时候显示名字 | 时间线 UI |
| `MinuteHit.kt` | 屏幕 y 坐标 → 第几分钟（点击反查） | 时间线 UI |
| `DurationWindow.kt` | 时长滑块的刻度范围怎么算 | 改时间面板 |
| `TemplateEngine.kt` | 给定模板 + 时刻，算出该铺哪些段 | 模板 |
| `TemplateEdit.kt` | 编辑模板时挪边界的规则（相邻段自动伸缩） | 模板编辑页 |
| `StatsCalc.kt` | 占比、汇总、趋势，口径的唯一权威 | 统计页 |
| `ChartGeom.kt` | 统计图的坐标换算 | 统计页 |
| `CalendarGrid.kt` | 月历排版（恒 42 格、周一起） | 月历组件 |
| `ColorSeries.kt` | 12 个色系 × 8 档，给事项自动配色 | 事项配色 |
| `DefaultTagInfer.kt` | 从历史推断事项的默认标签 | 数据库迁移 |
| `DayKey.kt` | `"2026-10-25"` 这个字符串的生成与解析 | 到处 |
| `Clock.kt` | 时间来源的抽象（测试可以拨表） | 到处 |
| `Outcome.kt` | 操作结果三态：Ok / Blocked / Failed | 到处 |
| `ImportSpec.kt` | 导入用的中间结构 | 导入 |

**`Clock.kt` 值得单独说**：所有「现在几点」都走它，而不是直接 `System.currentTimeMillis()`。
于是测试里可以造一个 `FakeClock.at("2026-10-14", 870)`，让「现在是 14:30」变成一个可控的值。
这是「跨天」「模板补算」这类逻辑能被测试的前提。

### `ui/` —— 界面层

| 包 | 文件 | 说明 |
|---|---|---|
| `ui/screen/` | 8 个 | 4 个主页面 + 4 个管理页 |
| `ui/sheet/` | 4 个 | 底部弹出的面板（选事项、改时间、改内容、操作菜单） |
| `ui/component/` | 3 个 | 通用组件（月历、各种小零件） |
| `ui/stats/` | 1 个 | 图表（Canvas 自绘） |
| `ui/theme/` | 3 个 | 配色、字体、主题 |

另外 `ui/` 根下还有几个 ViewModel 和 `PickerHost` / `PickerPrefs`。

### `cloud/` —— 云同步（可选）

| 文件 | 干什么 |
|---|---|
| `SyncEngine.kt` | 决定「哪些天要传」、分批、水位线 |
| `SyncClient.kt` | 发一个 HTTP 请求（只用 `HttpURLConnection`） |
| `SyncPrefs.kt` | 开关 / 地址 / token / 水位线，存在 SharedPreferences |

### `widget/` —— 桌面小部件

| 文件 | 干什么 |
|---|---|
| `TimelineWidget.kt` | Glance 的界面 |
| `WidgetModel.kt` | 小部件要显示的数据（纯逻辑，有测试） |
| `WidgetRefresh.kt` | 刷新时机（这里踩过一个大坑） |
| `QuickSwitchActivity.kt` | 在桌面上直接切事项（复用同一套选事项面板） |

## 深挖版：建议的阅读顺序

不要从头读。按这个顺序，每一站都能独立看懂：

### 第 1 站：`domain/Density.kt`（10 分钟）

最短的一个文件，但它是整个项目的**地基**：

```kotlin
// 检查一天是不是「密铺」的：从 0 开始、首尾相接、到 1440 结束
fun check(rows: List<RecordEntity>, dayMinutes: Int): List<String>
```

看懂它你就理解了「一天恒 1440 分钟」是怎么变成代码的。
配套测试 `DensityTest` 也就十几行，一眼看完。

### 第 2 站：`data/entity/RecordEntity.kt`（10 分钟）

一个时间段的全部信息。注意这几个字段是理解全局的关键：

| 字段 | 为什么存在 |
|---|---|
| `startMin` / `endMin` | 用**分钟**，不是时间戳 —— 跨时区、夏令时全都绕开 |
| `source` | `MANUAL` / `TEMPLATE` / `GAP`。GAP 就是「未记录」 |
| `noTemplate` | 「这**几分钟**别让模板填」（删过的地方） |
| `chainId` | 跨天同一条记录的两段共用一个 id |
| `categoryIdSnap` | 当时的分类快照（统计不用它，但留着做追溯） |

### 第 3 站：`TimelineRepository.pick()`（30 分钟）

「点了结束、选了一件事」之后发生的所有事。
这是全项目最密的一段业务逻辑，注释也最多。

### 第 4 站：`domain/TemplateEngine.kt` + `TemplateNoTemplateLockTest`（20 分钟）

纯函数 + 一条专门盯「模板运行中却不铺」的测试。
这条测试的注释本身就把那个 bug 讲清楚了，比文档还详细。

### 第 5 站：`ui/screen/TimelineScreen.kt`（20 分钟）

看看那些纯逻辑是怎么接到界面上的。注意它**很少自己做计算** ——
高度、点击、格式化，全调 `domain/` 里的函数。

## 三个「你可能会惊讶」的写法

**① 只有 1 个 Activity、0 个 Fragment**
五个页面全是 Composable 函数 + 一个 `when(route)` 分发。没有 Navigation 库。

**② 没有 DI 框架、没有 ViewModel 工厂**
`AppContainer` 手动 new 出来，`MainActivity` 往下传。
好处是「这个东西从哪来的」永远能一眼找到，坏处是传参有点长。

**③ 数据库迁移都带测试**
`Migration2To3Test` / `Migration3To4Test` 会建一个旧版本的库、灌入数据、
跑迁移、再逐条核对。迁移写错会静默丢数据，不测等于没做。
