# 06 · 数据怎么存的

> **30 秒版**：一个 SQLite 库、7 张表，`records` 是唯一的大表。
> 一天一条记录都不留也没关系 —— 因为所有的「没记」都存成了显式的 `GAP` 行。

---

## 30 秒版：表清单

| 表 | 一行是什么 | 大概多少行 |
|---|---|---|
| `records` | 一段（含「未记录」段） | 一年约 6000 行 |
| `categories` | 一级分类 | 10 |
| `items` | 二级事项 | 60 上下 |
| `tags` | 二级标签 | 8 上下 |
| `tag_buckets` | 一级标签（纯容器） | 3 |
| `record_tags` | 记录 ↔ 标签 的关联 | 记录数 × 1~2 |
| `item_default_tags` | 事项的默认标签 | 几十 |
| `templates` / `template_segments` / `template_run` | 模板与运行态 | 10 / 100 / 1 |
| `backup_snapshots` | 撤销用的快照 | 0~几条 |

数据库版本 **4**，有三个迁移（1→2、2→3、3→4），**每个都有测试**。

## 上手版：`records` 表

```sql
CREATE TABLE records (
    id           TEXT PRIMARY KEY,   -- 随机 id
    day          TEXT,               -- "2026-10-25"，字典序=时间序
    startMin     INTEGER,            -- 480 = 08:00
    endMin       INTEGER,            -- 570 = 09:30；NULL = 还在进行中
    itemId       TEXT,               -- 指向 items；GAP 段这里是 NULL
    categoryIdSnap TEXT,             -- 当时的分类（只留档，统计不用）
    source       TEXT,               -- MANUAL / TEMPLATE / GAP
    chainId      TEXT,               -- 跨天同一件事的两段共用一个值
    noTemplate   INTEGER,            -- 1 = 这几分钟别让模板填
    note         TEXT,               -- 备注
    updatedAt    INTEGER,            -- 毫秒时间戳（云同步靠它算增量）
    deleted      INTEGER
);
```

### 三个你一定会用到的查询

```kotlin
// 某一天的全部段（按时间顺序）
@Query("SELECT * FROM records WHERE day = :day AND deleted = 0 ORDER BY startMin")
fun byDay(day: String): List<RecordEntity>

// 一个区间内的（统计页用这个，别一天一天查）
@Query("SELECT * FROM records WHERE day BETWEEN :from AND :to AND deleted = 0 ORDER BY day, startMin")
fun between(from: String, to: String): List<RecordEntity>

// 云同步：哪些天在上次同步之后改过
@Query("SELECT DISTINCT day FROM records WHERE updatedAt > :since AND deleted = 0")
fun daysChangedSince(since: Long): List<String>
```

### `day` 为什么用字符串

`"2026-10-25"` 的**字典序恰好等于时间序**，所以：

- 区间查询可以直接 `BETWEEN '2026-10-01' AND '2026-10-31'`
- 排序不用转日期
- 跨时区不会变（这是「日期」不是「时刻」）

代价：校验必须严。`"2025-13-45"` 长得合法但根本不存在。
所以有个 `isDateStr` 做**回环校验**（解析回来必须等于原串）—— 这是踩过坑之后加的。

## 深挖版

### ① 为什么「未记录」要存成真实的行

大多数 App 会把它算出来（「1440 减去已记录的就是空白」）。这里不这么做，有两个理由：

**a. 空白需要「记住态度」**
你手动删掉的一小段和从未记过的空白，**语义不同**：
前者你说过「这里我不想让模板填」，后者没有。如果空白是算出来的，这个态度就没地方存。

**b. 空白是补记的入口**
它得是一个能点的东西。算出来的东西没有 id，点不了。

**c. 不想有第二个「空白怎么算」的定义处**
一旦读的时候现算，那么「补密的算法」和「统计的算法」迟早会分头漂移。
现在只有一处写空白（`ensureDense`），其它地方都读结果。

### ② 迁移：每次都只改数据，不加字段

三次迁移的共同点：**表结构没动，只改里面的数据**。

| 迁移 | 干了什么 | 为什么必须做 |
|---|---|---|
| 1→2 | 补一张模板表 | M2 有了模板功能 |
| 2→3 | 重新分配分类颜色（12 个色系） | 原来的 6 个颜色区分度不够 |
| 3→4 | 按历史推断事项的默认标签 | 旧版没有「默认标签」这个概念 |

⚠️ **3→4 那次查了很久才搞明白**：用户以为「迁移把我的标签弄丢了」，
实际上是**旧版根本没有这个概念**（标签只挂在记录上，事项上没有默认标签）。
查证方法是去看迁移之前的库 —— 那边也是 0 条。

所以迁移的守卫写得极保守：**已有数据整个跳过、只 INSERT 不 UPDATE、记录数少于 3 条的事项不推断**。
宁可少推，不能推错。

### ③ 「删除分类」为什么要拦

因为分类背后挂着事项，事项背后挂着几千条记录。删一个分类等于改几千条历史。

所以：**分类下有事项 → 拒绝删除**（先在界面上把事项搬走，才允许删）。
这条守卫写在 Repository 里，**不是只在界面上把按钮置灰** ——
界面只是提示，数据层才是防线。

### ④ 云端：可选，且约定很松

App 可以把改过的天增量上传到你自己的后端。**接口只有一个**：

```
POST {你的地址}/api/tl/sync
Authorization: Bearer {同步 token}

{
  "device":  "手机型号",
  "days":    [ { "d": "2026-10-25", "segs": [...] }, ... ],
  "meta":    { 事项/分类字典 }        // 每批都带，几 KB
}
```

几个设计决定：

| 决定 | 理由 |
|---|---|
| 增量传「改过的天」 | 一天几 KB，全量传没必要 |
| 水位线取**同步开始那一刻** | 用结束时刻会永久漏掉同步期间新写的记录 |
| `meta` 每批都带 | 「只最后一批带」中途失败会让云端分类名对不上 |
| 开关**默认关** | 往外传数据这件事，不给关就是耍流氓 |

⚠️ 仓库里**不含后端代码**。想用就自己搭一个，只要满足上面这个约定。
服务端建议**自己做密铺校验**（接不上、历史日没满 1440、铺到未来 → 整批拒收），
因为客户端永远可能是旧版本。

### ⑤ 数据能搬走吗

能，而且不用写代码：

- **导出**：`adb exec-out run-as com.misaka.timelog cat databases/timelog.db > 备份.db`
  （需要 debug 版；正式版要 root）
- **导入**：仓库自带 `data/import/LegacyImport.kt`，读一个约定的 JSON 就能全量替换
- JSON 的格式就是 `assets/legacy_timelog.json` 那个样子，`tools/gen_demo_data.py` 是生成器

⚠️ 导入是**全量替换**（先清空再写），并且会留一份快照，导错了能一键撤销。
