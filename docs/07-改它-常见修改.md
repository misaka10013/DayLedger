## 上手版：五个具体例子

### 例 1 · 改 App 的名字

三处，**都要改**：

1. **显示名**：`app/src/main/res/values/strings.xml` 里的 `app_name`
2. **包名**：`app/build.gradle.kts` 的 `applicationId` 和 `namespace`
   ⚠️ 改包名会导致「装不上」（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`），
   因为系统认为是另一个 App。已装的旧版要先卸。
3. **Kotlin 包目录**：`app/src/main/java/com/misaka/timelog/` 这个路径理论上一改就要动
   **所有文件的 package 声明**。

> 💡 建议：如果你只是想换个名字用，**只改 `applicationId` 和 `strings.xml`**，
> 别动 `namespace` 和目录。包名不好看又不影响功能。

### 例 2 · 加一个分类 / 改分类颜色

**如果是新装 App 的人**：改 `data/SeedData.kt` 里的 `CATS` 列表，卸载重装即可。

**如果已经装了、要保留数据**：在 App 里「设置 → 分类 → +」加，别改代码。
代码里的 `CATS` 只在**建库那一刻**写入一次，已经建好的库不会因为它变了而变。

⚠️ 这是新手最容易困惑的一点：**「我改了代码为什么 App 里没变？」**
—— 因为那个数据早就写进数据库了。改种子只影响全新的库。

颜色的分配还有一层：`CATS` 里写的色值不是最终颜色，
它会被 `domain/ColorSeries.kt` 分到 **12 个均匀色系**里（就近 + 冲突让位），
这样新加分类时不会和已有分类撞色。想完全控制颜色，界面上可以手动指定。

### 例 3 · 改选事项面板的列数

`ui/sheet/ItemPickerSheet.kt` 顶部：

```kotlin
private const val COLS = 6
```

改成 5 或 4，格子会变大。**只需要改这一个数字** ——
分组视图和聚合视图共用它，测试也是从这个常量取的。

⚠️ 但有两条底线别破：

- **一屏平铺、不要加分类筛选条、不要加搜索框**。这是产品的核心决定（见 [02](02-需求是怎么想的.md)）。
- 聚合视图里每行末尾有 `Spacer(weight(1f))` 补位。**删了它最后一行会被拉宽变形**
  （6 列时最后一行只有 3 个，会被撑成 3 个超宽格子）。

### 例 4 · 加一个统计视图

三步，缺一不可：

**① 算**（纯函数，加在 `domain/StatsCalc.kt`）
```kotlin
// 例：算「每个事项在这周内出现了多少天」
fun daysPresent(records: List<RecordEntity>, itemId: String): Int
```

**② 测**（`app/src/test/.../StatsCalcTest.kt`）
纯函数最大的好处就是这个测试**不需要建库**，构造几个 `RecordEntity` 就能跑。

**③ 画**（`ui/stats/Charts.kt` 里加一个 Composable，在 `StatsScreen.kt` 里挂上去）

⚠️ 两个坑：

- **几何计算别写在 Composable 里**。抽到 `domain/ChartGeom.kt`，不然没法测。
  「柱子画对了但点击热区没跟上」是最难查的一类 bug —— 不报错、不崩、截图也看不出来。
- **y 轴上限跟着峰值走**，不要写死 24 小时。否则数据少的时候柱子挤在底部一条缝。

### 例 5 · 加一个记录字段（比如「地点」）

这是**最重**的一种改动，因为要动数据库。完整步骤：

```
① data/entity/RecordEntity.kt     加 val place: String = ""
② data/TimeLogDatabase.kt          version = 4 → 5，写 MIGRATION_4_5
③ app/src/test/.../Migration4To5Test.kt   新建，照 Migration3To4Test 抄
④ data/import/LegacyImport.kt     解析 JSON 时读这个字段（可选）
⑤ 界面                           在哪显示、在哪编辑
```

⚠️ **迁移测试不是可选项**。迁移写错会**静默丢数据** ——
用户不会立刻发现，等他发现的时候已经没法追了。
`Migration3To4Test` 的做法是：建一个 v3 的库 → 灌数据 → 跑迁移 → 逐条核对。

## 深挖版：几条通用的修改纪律

### 纪律 1 · 改 UI 前先问「这个计算能不能抽出来」

判断标准：**如果它只跟时间/坐标/数据有关，跟 Android 无关，就该在 `domain/`。**

好处很直接：能写单元测试、能一秒钟跑一遍、能在 CI 上跑。

反例：把「这一段该显示名字还是显示时间」写在 Composable 里 ——
那就只能靠人眼看截图，而截图是**不可靠的**（作者曾经把浅灰柱看成「白缝」、
把 0 个琥珀像素看成「有红点」）。

### 纪律 2 · 任何「跟着 X 走」的显示，必须找到唯一入口

这是本项目栽过八次的地方。具体做法：

```
❌ var 显示数据 = 手动在三个地方各刷一次
✅ 一个 refreshAll()，三处都调它
```

加功能时如果发现「这里需要跟着某状态变」，先问：**这个状态的变化有没有一个统一的通知点？**
没有就先建一个，再往上加功能。

### 纪律 3 · 改完跑测试，别靠眼看

```bash
./gradlew :app:testDebugUnitTest
```

525 条，一分钟。比手动点十分钟靠谱得多。

⚠️ **Gradle 在后台跑的时候不要改源码** —— 编译会读到半成品，白等一轮。
作者为此浪费过两次六分钟。

### 纪律 4 · 判断「有没有这个功能」看数据变没变，不看按钮上写了什么

这条来自一次连环踩坑：界面上有个按钮，文案、位置、图标全对，
但它 `onclick` 是空的。连着踩了七次。

所以测试里有个规矩：**按钮该干的事，断言必须去点那个按钮**，
而不是 `eval("那个函数()")`。直接调函数会绕过按钮的接线 —— 而接线才是容易错的地方。

## 想删功能？

比加功能更需要小心，因为依赖是网状的。以「删掉模板」为例，至少要动这些地方：

```
data/repo/TemplateRepository.kt        ← 主体
data/repo/TimelineRepository.kt        ← applyTemplate() / syncTemplateDay() / fillableByTemplate()
data/entity/TemplateEntity.kt 等 3 个  ← 表
ui/screen/TemplateScreen.kt            ← 界面
ui/screen/TimelineScreen.kt            ← 顶部那条「模板运行中」
data/TimeLogDatabase.kt                ← 迁移里要 DROP TABLE
app/src/test/ 里 4 个测试文件           ← 一起删，否则编译不过
```

**建议顺序**：先把界面入口藏掉（改一个 `if`），跑一段时间确认没人用，再删内核。
一上来就从数据层删，最容易删出一个「编译能过、运行就崩」的版本。
